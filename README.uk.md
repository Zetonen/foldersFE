# Data Room — Frontend

**Українська** · [English](README.md)

Віртуальна кімната даних: PDF-файли у вкладених теках, завантаження з
прогресом по кожному файлу, доступ «тільки для читання» за посиланням або для
конкретних людей.

Цей репозиторій містить **лише фронтенд**. API живе в окремому репозиторії і
деплоїться незалежно.

## Запуск

Потрібен **Node 20.19+ або 22.12+** (вимога Vite 7).

```bash
npm ci
cp .env.example .env     # за замовчуванням вказує на задеплоєний API
npm run dev              # http://localhost:3000
```

| Скрипт                 |                                                   |
| ---------------------- | ------------------------------------------------- |
| `npm run dev`          | дев-сервер на порту 3000                          |
| `npm run build`        | перевірка типів (`tsc -b`), потім продакшн-збірка |
| `npm run preview`      | локальний перегляд продакшн-збірки                |
| `npm run lint`         | ESLint                                            |
| `npm run format`       | Prettier, із записом                              |
| `npm run format:check` | Prettier, лише перевірка                          |

**Змінні середовища** — одна, `VITE_API_BASE_URL`. Читається один раз на старті,
і додаток одразу падає, якщо її немає, замість того щоб тихо слати запити на
власний origin.

> Дев-сервер займає порт 3000, тож локальний бекенд має бути на іншому.

## Архітектура

Шари, ззовні всередину. **Імпорти йдуть тільки вниз**, і це форситься через
ESLint (`no-restricted-imports`), а не тримається на домовленості — див.
[`eslint.config.js`](eslint.config.js).

```
pages/       роутові компоненти і сам роутер
widgets/     самодостатні блоки екрана (модалки, хедер, сайдбар)
features/    одна користувацька можливість (черга завантажень, доступи, PDF-переглядач)
components/  layout/  каркаси сторінок
             moduls/  перевикористовувані елементи рівня додатка
             ui/      примітиви shadcn
shared/      хуки, хелпери, константи — нічого не знають про фічі
api/         ендпоінти RTK Query, інстанс axios, схеми відповідей
store/       слайси і персистенція
types/       DTO-схеми та спільні типи
```

Модуль із `features/` не може імпортувати іншу фічу, віджет чи сторінку.
Віджет не може імпортувати сторінку чи інший віджет. Саме це тримає екран
складаним: кожна залежність або спрямована вниз, або передається пропсом.

Кожен модуль — це тека з `components/`, `hooks/`, `helpers/`, `constants/` і
барелом `index.ts`. Тому у файлі компонента лежить розмітка, а потрібна йому
логіка — поруч, під назвою, яка каже, що вона робить.

## Проєктні рішення

### Серверний стан живе рівно в одному місці

RTK Query володіє всім, що прийшло з API. Слайси Redux тримають лише те, чого
сервер не знає: сесію, режим перегляду, стан сайдбара, чергу завантажень,
поточне виділення. **Жоден слайс не дублює серверні дані** — тож немає кешу,
який треба інвалідувати двічі, і немає шансу, що ці двоє розійдуться.

### Кожна відповідь валідується до потрапляння в кеш

`axiosBaseQuery` приймає необов'язкову Zod-схему і парсить тіло відповіді ще до
передачі в кеш ([`src/api/baseQuery.ts`](src/api/baseQuery.ts)). Тіло, що не
збігається зі схемою, повідомляється як помилка сервера, замість того щоб
потекти в компоненти неправильно типізованим об'єктом. DTO-схеми в
`src/types/models/` — єдине джерело правди і для рантайм-перевірки, і для
статичного типу.

### Access-токен ніколи не потрапляє на диск

`FR-STATE-04`. Токен живе тільки в пам'яті і явно виключений із `redux-persist`;
refresh-токен — це httpOnly-кука, якої JS не бачить. На кожному свіжому
завантаженні сесія відновлюється одним запитом `/auth/refresh`, а роутові гарди
тримають лоадер, доки це не завершиться — інакше перезавантаження глибокого
посилання викидало б користувача на `/login` ще до того, як сесія встигла б
повернутися.

401 на будь-якому запиті чистить сесію і редіректить, зберігши поточний шлях у
`?next=`. Логін, реєстрація і refresh **виключені** з цього глобального
обробника: 401 там означає «невірні дані», а не «сесія протухла», і редірект на
екран логіну з екрана логіну був би нонсенсом.

### Завантаження — транзакція з трьох кроків

1. **Резерв** — `POST /files/upload-url` повертає підписаний URL і вільне ім'я.
2. **Передача** — байти йдуть напряму в blob-сховище, повз API. Це єдиний запит,
   прогрес якого бачить користувач, і саме тому він не може жити в RTK Query.
3. **Підтвердження** — `POST /files/confirm` перетворює завантажений об'єкт на
   запис у базі.

Чергою керує один процесорний хук, змонтований в оболонці додатка, тож передачі
**переживають навігацію** між теками й екранами. Файли йдуть по одному: панель
показує смужку прогресу для кожного, і послідовна передача робить це число
осмисленим.

Об'єкти `File` не серіалізуються, тож стор тримає лише їхні метадані, а самі
блоби припарковані в module-level реєстрі під тими ж id. Реєстр звіряється з
чергою на кожну зміну — завантаження, що покинуло чергу, віддає свій блоб, а
_невдале_ його зберігає, щоб повтор не змушував користувача обирати файл знову.

Транспортні збої повторюються двічі зі зростаючою затримкою. Відмова — не той
тип, завеликий, не дозволено — остаточна, бо повтор дасть ту саму відповідь.

### Конфлікт імен вирішується до того, як зрушить перший байт

Сервер не відхиляє зайняте ім'я — він повертає вільне. Тому **ім'я, яке
повернулося зміненим, і є авторитетною ознакою конфлікту** — і єдиною
перевіркою, що бачить усю теку, а не ті сторінки, які встиг завантажити цей
клієнт. Резервування нічого не створює (ні запису, ні об'єкта — лише підписаний
URL), тож відкинути його нічого не коштує. Саме це робить безпечним питати
користувача в цей момент.

«Замінити» потім завершується в єдиному порядку, який не може втратити файл:
спершу зберігається новий, _потім_ зникає старий, _потім_ ім'я переходить.

### Клієнт ніколи не вирішує, що користувачеві можна

API віддає роль викликача (`myRole`) разом із кожною текою, файлом і лістингом.
Клієнт лише її відображає. Дії, на які немає прав, **не рендеряться взагалі**, а
не рендеряться задизейбленими — глядачеві не варто показувати двері, які він не
може відчинити.

### Оптимістичні оновлення зі справжнім відкатом

Перейменування, переміщення і видалення правлять закешований лістинг на місці,
тож зміна видно ще до того, як запит завершиться. Кожен хелпер кешу — no-op,
якщо елемента немає у завантажених сторінках, і саме це робить відкат безпечним
для беззастережного застосування.

Переміщення супроводжується тостом Undo, вираженим як те саме переміщення з
переставленими кінцями.

### Лістинг великих тек

Keyset-пагінація (`nextCursor`) плюс нескінченний скрол, а тіло таблиці
віртуалізоване через `@tanstack/react-virtual` — DOM лишається сталого розміру
незалежно від того, скільки сторінок уже завантажено. `null` і тільки `null`
означає, що лістинг вичерпано; коротка сторінка — ні.

### Бандл

`manualChunks` розділяє вендори, щоб реліз не інвалідував усе одразу, а pdf.js —
найбільша залежність із великим відривом — замкнений у лінивому чанку, який не
завантажується, доки не відкрито файл. PDF-переглядач рендерить вікно сторінок
навколо поточної, а кожній іншій дає плейсхолдер її реальної виміряної висоти,
щоб скролбар лишався чесним, поки нічого не намальовано.

## Граничні випадки

| Випадок                                         | Обробка                                                                                                        |
| ----------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| Завантаження з іменем, що вже є в теці          | Питаємо до передачі; «Лишити обидва» / «Замінити» / «Пропустити», із «застосувати до всіх»                     |
| Два файли з однаковим іменем в **одному** батчі | Конфліктують між собою так само, як конфліктували б з наявними                                                 |
| Видалення теки                                  | Попередження з підрахунком усього піддерева, що буде знищене                                                   |
| Видалення теки, яку хтось переглядає            | Глядач потрапляє на екран 404/Forbidden, а не в порожню рамку                                                  |
| Втрата зв'язку                                  | Офлайн-банер; черга завантажень стає на паузу і продовжується після відновлення                                |
| Закриття вкладки під час завантаження           | Запит `beforeunload`, поки є активні передачі                                                                  |
| Протермінований або відкликаний лінк            | Окремий екран «посилання недійсне»                                                                             |
| Ліміт запитів (429)                             | Одне вікно очікування блокує дії, які все одно впали б; читає `Retry-After` і бекендівський `Retry-After-auth` |
| Лінивий чанк не завантажився                    | Роутовий error boundary пропонує перезавантаження, а не повтор того самого запиту                              |
| Скасовані запити                                | Мовчать — ніколи не показуються тостом                                                                         |
| Довгі імена файлів                              | Обрізаються в рядку, повне ім'я — в тултипі                                                                    |
| OAuth-колбек, якого ця вкладка не починала      | `state` звіряється зі значенням, збереженим у `sessionStorage`                                                 |

## Де використовувався AI

Я користувався AI (Claude) як робочим інструментом протягом усієї роботи, у
трьох напрямках:

**Генерація коду.** Компоненти й хуки здебільшого чернетково писав AI за
специфікацією, яку я складав для кожного модуля — черга завантажень, панель
доступів, віконний рендеринг PDF-переглядача, обробники drag-and-drop. Я
переглядав і переробляв результат, а не брав як є; описана вище поведінка при
взаємодії та помилках — результат кількох проходів, а не першої чернетки.

**UI та стилі.** Композицію Tailwind-класів і примітиви shadcn/Radix у
`src/components/ui/` було згенеровано і потім допрацьовано — відступи, кольорові
токени в `src/styles/`, адаптивна поведінка сайдбара й панелі деталей.

**Рев'ю та рефакторинг.** Я проганяв AI-рев'ю по готовому коду, щоб знайти
мертвий код і неузгодженості. Звідти й останнє прибирання: видалення покинутого
шару обробки помилок на `neverthrow`, яким користувалася лише одна функція;
видалення невикористаних хуків і залишків стартового шаблону; виправлення
витоку, через який блоби скасованих завантажень лишалися в пам'яті до кінця
життя вкладки; виправлення маніфесту залежностей (`pdfjs-dist` імпортувався, але
не був оголошений); нормалізація закінчень рядків і форматування.

**Що я не делегував.** Архітектура моя: шари й правила імпортів, які їх форсять;
рішення віддати RTK Query володіння всім серверним станом; тримання
access-токена поза сховищем; трикроковий аплоад і той порядок, який робить
«Замінити» безпечним; відображення виданих сервером ролей замість обчислення
прав на клієнті. AI написав чимало коду — але форма рішення й компроміси вище
мої, і кожен із них я можу захистити.
